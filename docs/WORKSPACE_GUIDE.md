## Why this structure
- `routes/` maps URL → page component, not a home for business logic.
- `features/` owns feature components, API adapters, data hooks, validation and domain code.
- `lib/api` is the only place HTTP requests are constructed. When backend URL/contracts change, you update adapters, not every page.
- `domain/` defines the request/response types. Prefer schema-generated types from OpenAPI after agreement.
- `mocks/` allows development before backend is ready; disabled in production builds.
- Admin and POS are deliberately separate experiences (SRS UI-01 and UI-15).

## Your first team-project workflow
1. `git switch test && git pull origin test` **only if your team's integration branch really is `test`**.
2. `git switch -c feature/admin-architecture` (or use your existing feature branch).
3. Review this sample workspace separately, cherry-pick only the files your team approves. Never overwrite teammate code without review.
4. `npm ci`, copy `.env.example` to `.env.local`, `npm run dev`.
5. Demo: `http://localhost:3000/login`, admin@mifta.example / demo12345 in **dev-only mock mode**.
6. Add only relevant files; commit and push your feature branch, then PR to the agreed integration branch.

## Integration notes / quality gates
- Never run real payments, real orders or print tickets with this starter; those flows are intentionally scaffolded.
- Current starter supports admin navigation, searching mock records, a demo authentication boundary, local POS cart interaction and channel repricing (chain price fallback only).
- Not yet complete: API mutations, real PIN auth, manager override, optional item modifiers, delivery fees, branch overrides, live calls, printing, GDPR operations, offline IndexedDB sync, VAT reporting, tests and security review.
- Keep business rules on the backend. Frontend role visibility is not security.
- Before release: verify 1024×768 on current hardware, keyboard-only and touch operation, SRS UI-19 staff trial, E2E tests and SRS Q1–Q17 open client questions.
